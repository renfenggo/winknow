# 第 10 周交付：混淆方案评估（.NET 8 兼容性）

> 任务来源：V7.0 计划书第 10 周"混淆方案评估——选择兼容 .NET 8 的维护方案"。
> 结论先行：**基础版选择"符号重命名（公共 API 保留）+ 程序集签名 + IL 自校验"组合**，
> 不引入重型加壳（原因见 2.3），.NET 8 全兼容。

## 2. 评估结论

### 2.1 基础版选定方案：轻量混淆三件套

1. **符号重命名（保留公共 API）**
   - 对 `Winknow.Security`、`Winknow.ProcessControl`、`Winknow.Network`、`Winknow.DeviceSecurity` 内部类型/私有成员重命名；
   - 公共 API（IPC 协议类型、`Result`/`ErrorCode`、可扩展点）保留原名——命名管道协议与 JSON 序列化依赖公共类型名，重命名会破坏跨进程通信与既有测试；
   - 实现：Dotfuscator Community（VS 2022 内置）或 ConfuserEx 2 的 rename 阶段。
2. **字符串轻度混淆**：策略关键字（进程名清单、注册表路径）经简单编码，提高课堂环境逆向门槛——不追求对抗专业逆向。
3. **Authenticode 强签名 + 自校验**：`TrustedUpdater` 已实现更新包签名校签（第 7 周），叠加第 10 周 `PeerVerifier` 对运行文件的 Hash/签名校验，篡改后无法通过守护拉起——混淆失效的兜底防线是签名而非混淆本身。

### 2.2 不选重型加壳的理由

- 课堂部署环境（EDU 管控软件）常被杀软重点关照，加壳反而提高误报与部署成本；
- 加壳与 AOT/裁剪和 Windows 服务宿主（`Microsoft.Extensions.Hosting.WindowsServices`）的兼容矩阵复杂，维护成本超过安全收益；
- 威胁模型定位：对手是"学生绕过管控"而非"专业逆向团队"——混淆目标是抬高门槛，签名链才是完整性根。

### 2.3 .NET 8 兼容性要点

- 传统 .NET Framework 混淆器（旧版 Dotfuscator、Crypto Obfuscator）不支持 .NET 8 程序集，**选型时必须确认其支持 Roslyn/RyuJIT 产物**；
- `System.Text.Json` 源生成与反射序列化对重命名敏感：本方案保留公共类型名，规避该风险；
- WPF（AdminUI）混淆需关闭 XAML 绑定路径重命名（`x:Bind`/`Binding` 路径含私有成员名）。

### 2.4 实施排期建议

- 第 12 周安装器制作时引入混淆构建目标（`dotnet obfuscat` 后置构建步骤）；
- 混淆产物必须重跑全量测试（公共 API 未重命名，理论上无影响，以测试实证）；
- 签名脚本在 CI 的受控环节执行，密钥不出 HSM（对应第 9 周密钥清单 CodeSigning 条目）。

## 3. 验收对照

- ✅ 选择兼容 .NET 8 的维护方案：三件套全部兼容，评估完成；
- ✅ 方案可落地：不阻塞当前构建（混淆为发布后置步骤）；
- ✅ 与既有安全设施正交：签名/Hash 校验（第 7、10 周）不依赖混淆，混淆仅为纵深防御一层。
