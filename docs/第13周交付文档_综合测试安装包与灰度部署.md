## 三、架构与流程设计

### 3.1 WMI 弹性重连（本周核心补强）

```
ManagementEventWatcher
   │ StartWatcher 异常 ────────────┐
   │ Stopped 事件（WMI 服务重启）─┤
   ▼                              ▼
ScheduleReconnect（Interlocked 互斥：并发触发只进一个）
   │ Task.Run：等待 WatcherReconnectPolicy.OnWatcherFailure() 退避
   │   失败1→1s  失败2→2s  失败3→4s … 封顶 60s
   ▼
TeardownWatcher（解除旧事件）→ StartWatcher（重建）
   │ 成功收到事件 → OnSuccess()：连续失败归零（累计 ReconnectCount 不减）
   │ 连续失败 ≥5 → IsPersistentlyFailing（供上层健康观测/日志告警）
   ▼
兜底不变：周期扫描（2s）仍在，watcher 失效期间窗口不扩大
```

补强前的缺口：watcher 因 WMI 服务重启静默 `Stopped` 后**永不重建**，进程实时发现退化为仅周期扫描；计划书风险表"WMI 事件丢失或监听断开 → 监听重建"一项此前未真正落地。`ReconnectCount` 同时满足灰度观察指标 #3 的采集口径。

        └─ release_manifest.json（178 文件 SHA256）

### 6.1 本次实现细节

1. **弹性重建的并发安全**：`ScheduleReconnect` 用 `Interlocked.Exchange` 抢占重建权——`Stopped` 事件与启动异常可能并发触发，只允许一个重建循环存在，其余直接返回。
2. **主动停与意外停的区分**：`Stop()` 先置 `_running=false` 再 Teardown，`OnWatcherStopped` 首行检查 `_running`——服务正常停机不会触发"幽灵重连"。
3. **退避与累计分离**：`OnSuccess` 只归零连续失败计数，`ReconnectCount` 单调递增——前者驱动退避曲线，后者是灰度健康指标，语义不同不能混用。
4. **策略类与监视器解耦**：`WatcherReconnectPolicy` 无 WMI 依赖（假时钟可测），监视器只做编排——8 项测试全部无权限/无真实 WMI 依赖。
5. **安装布局与运行时约定一致**：服务装 `{commonappdata}\Winknow\deploy\Current` 而非 `{app}`——第 7/10 周的 DeploymentSlots 切换、PeerVerifier、HeartbeatLease 全部按该路径工作，安装器若另起布局会导致 A/B 更新失效。
6. **策略 onlyifdoesntexist**：现场调过的策略文件不被升级覆盖——误覆盖是灰度阶段最常见的"莫名回退"来源。
7. **manifest 三方同构**：`release_manifest.json` 与 RecoveryVault/PeerVerifier 的清单同为"相对路径 + SHA256"约定——发布产物、恢复快照、对等核验共用一套校验语义。
8. **签名两种模式的原因**：自签名证书无信任链，`verify /pa` 必失败——测试模式改为指纹匹配断言（证明"签名动作生效且未被篡改"），生产模式保留完整验链；两者验证目标不同，不是绕过。
