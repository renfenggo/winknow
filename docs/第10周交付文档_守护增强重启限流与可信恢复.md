# 编程课堂电脑管控系统 V7.0 —— 第 10 周交付文档：守护增强、重启限流与可信恢复

> **里程碑**：M10 守护与恢复完成
> **周期**：第 10 周（心跳租约、单实例、对端验证、指数退避、重启阈值、Safe Degraded Mode、Recovery 目录、自动修复、混淆方案评估、崩溃循环测试）
> **基线**：V7.0 密钥与日志完整性版（第 9 周交付，提交 `66a9eba`）
> **目标**：避免双进程无限拉起（重启风暴），并实现核心文件损坏自动恢复——守护从"服务停了就拉起"升级为"验证可信才拉起、拉不起就降级保底、降级中持续修复"
> **验收标准**：不出现重启风暴；核心文件损坏后自动恢复；恢复失败时不自动全部放行；更新模式不会触发交叉拉起

## 三、架构与流程设计

### 3.1 守护决策链（GuardService.Worker，每 5 秒一轮）

```
                      ┌─────────────────────┐
                      │ ①更新模式标志有效？   │──是──> 暂停干预（防交叉拉起）
                      └──────────┬──────────┘
                                 │否
                      ┌──────────▼──────────┐
                      │ ②心跳租约存活？       │──是──> 退避归零；窗口冷却+降级冷却
                      └──────────┬──────────┘        期满→退出降级
                                 │否（死亡/僵死）
                      ┌──────────▼──────────┐
                      │ ③已处降级？          │──是──> 60s 周期 CheckAndRepair：
                      └──────────┬──────────┘        成功→等租约自愈
                                 │否                  失败→锚点告警，保持最低管控
                      ┌──────────▼──────────┐
                      │ ④限流窗口超阈值？     │──是──> EnterDegraded + 首次修复
                      └──────────┬──────────┘
                                 │否
                      ┌──────────▼──────────┐
                      │ ⑤退避到点？          │──否──> 本轮跳过
                      └──────────┬──────────┘
                                 │是
                      ┌──────────▼──────────┐
                      │ ⑥对端四重验证        │──失败→ 拒拉起 + EnterDegraded + 修复
                      │ 路径/签名/版本/Hash  │
                      └──────────┬──────────┘
                                 │通过
                      ┌──────────▼──────────┐
                      │ ⑦拉起服务           │ 成功→计入限流窗口
                      │ (僵死实例先Stop再Start)│ 失败→退避升级
                      └─────────────────────┘
```

### 3.2 防重启风暴双闸门

| 闸门 | 控制维度 | 参数 | 失效场景兜底 |
|------|----------|------|--------------|
| 指数退避 | 两次拉起**间隔** | 1s→2s→4s→…→60s 封顶（+抖动） | 启动即崩：`Reset` 仅由"观察到租约存活"触发，崩溃序列持续升级 |
| 重启限流 | 窗口内**频次** | 10 分钟 / 5 次 | 退避被绕过（如时钟异常）时仍有硬上限；超限直接转降级 |

双闸门叠加：20 次连续异常退出实际只发生 **5 次**拉起（见 4.1 崩溃循环测试）。

### 3.3 可信恢复优先级链（AutoRepairService）

```
CheckAndRepair
     │
     ├─ Current 健康 ────────────────────> AlreadyHealthy（无操作）
     │
     ├─ 策略① Recovery Vault 逐文件恢复
     │    └─ 全部恢复 + 复验健康 ────────> Repaired(VaultFileRestore, n)
     │         （复验防恢复源本身被污染）
     │
     ├─ 策略② Previous 槽整目录回滚
     │    └─ 回滚成功 + 刷新快照 ────────> Repaired(PreviousRollback)
     │
     └─ 全部失败 ───────────────────────> Failed（Detail 含"保持降级，不放行"）
                                          调用方维持 SafeDegradedMode
                                          └─ ShouldKeepMinimumControl = true（Fail-Closed）
```

### 3.4 双进程与交叉拉起防线（三层）

| 防线 | 机制 | 覆盖场景 |
|------|------|----------|
| 第 1 层 | ControlService 启动抢 `Global\` Mutex，后启动者退出 | 守护拉起与 SCM 自恢复/手工 start 竞争；新旧版本并存 |
| 第 2 层 | 更新窗口 `UpdateModeFlag`：更新器 Stop→切换→Start 期间守护暂停拉起 | 更新中途守护"好心"拉起造成新旧交叉 |
| 第 3 层 | 对端验证 Hash/签名：切换未完成的目录不可信，拒绝拉起转修复 | 标志被删/失效后的残余风险（收益仅"暂缓拉起"，无放行） |

### 3.5 与既有周次的衔接

- **第 7 周部署槽**：RecoveryVault/AutoRepairService 复用 `DeploymentSlots`（Current/Previous/Staging 同一 deploy 根）；更新成功后可 `RefreshSnapshot` 对齐 Recovery 与新 Current；
- **第 9 周事件锚点**：守护状态转移（EnterDegraded / ExitDegraded / PeerVerifyFailed / RepairFailedKeepDegraded / AutoRepairInDegraded）全部写入 `EventLogAnchor`（9001/9003），审计数据库不可用时 Windows 事件日志仍可追溯守护行为；
- **第 6 周 SCM 自恢复**：`ServiceRecovery`（异常退出自动重启）与守护互补——SCM 管单次崩溃拉起，守护管活性语义（僵死识别）与风暴抑制。

### 6.1 本次实现细节

1. **组件归属遵循 14 生产项目架构约束**：守护策略（纯逻辑）→ Core/Guarding；跨服务活性协商（文件级 IPC）→ Ipc；身份与信任（加密/签名）→ Security；可信恢复（部署文件操作）→ TrustedUpdater 复用 DeploymentSlots。新增 `Winknow.Guard.Tests`（测试项目不计入架构约束）。

2. **退避归零的语义选择**：`backoff.Reset()` 仅在"观察到租约存活"时触发，而非"服务启动成功"——启动命令成功但 1 秒后崩溃的序列会持续升级退避，而非每次都从 1s 重新开始。

3. **僵死实例处理**：`TryRestartService` 遇到 Running 但租约失效的实例执行 Stop→Start（Worker 第 ②/⑦ 步注释），补齐"服务活着但没在干活"这一纯进程/服务状态检测永远无法覆盖的场景。

4. **修复后复验**：Vault 恢复成功后立即重新 `VerifyAgainstManifest`——若恢复源本身被污染（攻击者同时篡改 Current 与 Recovery），复验失败自动降级到 Previous 回滚，不会带着"假修复成功"继续运行。

5. **更新标志新鲜期**：10 分钟上限 > 最长更新流程（服务停止 30s×2 + 切换 + 健康检查），且陈旧自动失效——协调机制自身不能成为新的单点故障。

6. **事件锚点限频**：守护状态转移（而非每轮循环）才写锚点，避免 5 秒级循环刷爆 Windows 事件日志；持续降级期间的告警由 60s 修复周期自然限频。

7. **单实例退出的副作用控制**：ControlService 获锁失败直接 `return`——不初始化 IPC/策略/网络任何设施，避免双实例重复执行进程拦截与策略下发（比"初始化后再退出"安全）。
